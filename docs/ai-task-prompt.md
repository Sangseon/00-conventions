# AI Task Prompt Convention

AI 개발 도구에 전달하는 작업 프롬프트의 작성 및 검증 기준을 정의한다.

특정 AI 도구나 프로젝트에 종속되지 않고, 작업의 목적과 현재 상황에 맞춰 명확하고 검증 가능한 지시문을 작성하는 것을 목표로 한다.

## 1. Purpose

이 Convention은 Codex, Claude Code 등 AI 개발 도구를 활용하는 소프트웨어 개발 작업 요청에 적용한다.

- 작업 목적과 기대 결과를 명확히 전달한다.
- 현재 코드·문서·설계 정책에 근거해 작업하도록 한다.
- 작업 범위와 제외 범위를 구분한다.
- 기존 기능과 프로젝트의 일관성을 유지한다.
- 실제 수행한 검증과 수행하지 않은 검증을 구분한다.
- AI 도구가 달라져도 일관된 작업 요청 기준을 유지한다.

이 문서는 프롬프트 **작성 규칙**이며, 모든 요청에 동일한 목차·문장·분량을 적용하는 고정 템플릿이 아니다.

## 2. Common Principles

### 2.1. 목적과 결과의 명확성

작업의 대상, 기대 동작, 완료 판단 기준을 가능한 한 구체적으로 제시한다. 구현 방법을 불필요하게 고정하기보다 지켜야 할 요구사항을 우선 설명한다.

### 2.2. 확인된 사실과 추정의 구분

이전 대화나 설명만으로 현재 프로젝트 상태를 확정하지 않는다. 필요한 경우 최신 코드, 설정, 테스트 및 문서를 직접 확인하도록 요청한다.

확인된 사실, 가정, 추가 검증이 필요한 내용을 구분하며 실제 확인하지 않은 내용을 확인했다고 보고하지 않는다.

### 2.3. 기존 설계의 존중

기존 아키텍처, 기술 선택, 코딩 규칙과 프로젝트 정책을 우선 확인한다. 신규 의존성이나 구조 변경이 필요하면 그 이유와 Trade-off를 검토하도록 한다. 새로운 기술이라는 이유만으로 기존 구현을 교체하지 않는다.

### 2.4. 작업 범위의 통제

요청과 직접 연관된 변경을 중심으로 작업한다. 관련 없는 기능 추가, 추후 단계의 선행 구현, 불필요한 리팩터링을 지시하지 않는다.

### 2.5. 검증의 정직성

실행·테스트가 가능한 작업은 적절한 검증을 요청한다. 테스트 성공을 추정하지 않고, 실행 결과와 제한 사항을 명시하도록 한다.

### 2.6. 작업 규모에 맞는 상세 수준

간단한 수정은 간결하게, 복잡하거나 위험한 변경은 충분히 구체적으로 작성한다. 공통 항목을 기계적으로 모두 나열하지 않는다.

### 2.7. 지속 지침과 일회성 요청의 구분

`AGENTS.md`, `CLAUDE.md` 등 프로젝트 지침 파일이 있으면 해당 도구에 실제 적용되는 지침을 확인하도록 한다.

반복적으로 적용되는 프로젝트 규칙은 프로젝트 지침에서, 특정 작업의 목표·범위·완료 기준은 작업 프롬프트에서 다룬다. 중요한 제약은 필요할 때 프롬프트에도 명시할 수 있다.

지침 파일의 작성·관리 규칙은 별도의 AI Project Instructions Convention에서 다룬다.

## 3. Base Prompt Structure

작업 프롬프트는 다음 공통 정보 중 해당 작업에 필요한 항목을 포함한다.

| Component    | Description                                 |
| ------------ | ------------------------------------------- |
| Context      | 프로젝트 배경과 현재 상태, 참고할 코드·문서 |
| Objective    | 이번 작업의 목적과 기대 결과                |
| Requirements | 구현·분석·변경할 내용과 완료 기준           |
| Constraints  | 유지해야 할 정책, 변경 금지 사항, 제외 범위 |
| Validation   | 수행할 검증과 성공 판단 기준                |
| Deliverables | 필요한 산출물 및 완료 보고                  |

항목을 모두 독립된 Section으로 만들 필요는 없다. 하나의 문단으로 합치거나 불필요한 항목을 생략해도 되지만, 작업 대상과 범위, 기대 결과가 모호해져서는 안 된다.

### 3.1. Context

필요한 경우 프로젝트명, 실행 환경, 기술 스택, 관련 파일, 선행 작업 상태를 제공한다. 제공한 배경 설명보다 실제 저장소 상태가 우선 확인되어야 한다.

### 3.2. Objective

이번 작업이 해결할 문제와 기대 결과를 정한다. 목표가 여러 개면 주 목표와 부가 목표를 구분한다.

### 3.3. Requirements

필수 요구사항, 선택 사항, 오류·경계 조건 및 완료 기준을 필요한 수준으로 기술한다. 구체적인 방법을 강제할 이유가 없다면 구현 방식의 선택 여지를 남긴다.

### 3.4. Constraints

기존 동작·API·데이터 정책 유지, 변경 대상 제한, 의존성 제한 등 중요한 제약을 명시한다. 프로젝트 지침에 있는 공통 규칙은 불필요하게 반복하지 않는다.

### 3.5. Validation

변경 내용에 대응하는 테스트, 실행 확인, 회귀 검증과 성공 기준을 정의한다. 검증의 종류는 작업 성격과 환경에 맞춘다.

### 3.6. Deliverables

변경 파일, 문서, 검증 결과, 미완료 항목 등 최종적으로 확인할 산출물을 정한다. 보고 수준은 작업 규모에 맞게 조절한다.

## 4. Task-Specific Guidelines

작업 유형별 지침은 Base Prompt를 보강하기 위한 선택 항목이다. 하나의 요청에 여러 유형을 적용할 수 있다.

### 4.1. Feature Implementation

신규 기능 또는 기존 기능 확장에서는 다음을 필요에 따라 다룬다.

- 사용자 관점의 기대 동작과 입출력·상태 변화
- 기존 구성 요소와 연동하는 방식
- 정상·오류 흐름 및 경계 조건
- 데이터·연결·미디어 등 자원 생명주기
- 기존 기능과의 호환성, 완료 기준, 테스트 및 문서화

다음 개발 단계의 기능을 미리 구현하지 않도록 범위를 정한다.

### 4.2. Bug Analysis and Fix

- 증상, 재현 조건, 기대 동작과 실제 동작
- 재현 및 원인 분석, 영향 범위
- 수정의 선택 이유와 필요한 최소 변경
- 정상 흐름 및 오류 흐름의 회귀 검증
- 재현이 어렵거나 확정하지 못한 부분

원인을 확인하기 전에 특정 수정안을 정답으로 전제하지 않는다. 증상 완화와 근본 원인 해결을 구분한다.

### 4.3. Refactoring

- 개선하려는 구조적 문제와 목적
- 변경 전후에 유지할 외부 동작
- 구조 변경 범위와 영향
- 동작 동등성 및 회귀 검증

명시적으로 요청하지 않았다면 기능이나 업무 정책을 변경하지 않는다.

### 4.4. Design Review

- 해결할 문제와 기존 설계·제약
- 대안과 각 대안의 Trade-off
- 복잡도, 성능, 안정성 및 유지보수성
- 권고안의 근거와 남은 위험

설계 검토만 요청한 경우 실제 구현을 수행하도록 지시하지 않는다.

### 4.5. Code Review

- 검토 대상과 평가 기준
- 정확성, 예외·경계 처리, 동시성, 자원 관리
- 보안, 성능, 유지보수성 및 기존 설계와의 일관성
- 문제의 위치·근거·영향·개선 방향

확인된 결함과 잠재적 위험, 의견 수준의 개선 사항을 구분한다.

### 4.6. Testing and Validation

- 검증 대상, 성공 조건, 정상·오류 시나리오
- 경계값, 상태 전이 및 회귀 조건
- 사용한 테스트 환경과 실제 실행 방법
- 테스트 한계 및 미검증 사항

Mock·시뮬레이션·가상 장치 검증을 실제 운영 환경이나 물리 장치 검증과 혼동하지 않는다.

### 4.7. Documentation

- 문서 목적과 대상 독자
- 관련 코드·기존 문서에 대한 사실 확인
- 실제 구현과 계획의 구분
- 용어, 구조, 링크 및 다른 문서와의 일관성

구현하지 않은 기능을 완료했다고 기술하지 않는다.

## 5. Combining Task Types

주요 작업 유형을 먼저 정하고, 필요할 때 다른 유형의 검증·분석·문서화 지침을 조합한다.

| Primary Task           | Additional Tasks       | Example                           |
| ---------------------- | ---------------------- | --------------------------------- |
| Feature Implementation | Testing, Documentation | 기능 구현과 실행 검증 및 기록     |
| Bug Analysis and Fix   | Testing                | 재현·원인 수정·회귀 검증          |
| Refactoring            | Design Review, Testing | 설계 비교 후 동작 보존 검증       |
| Design Review          | Code Review            | 현재 코드 분석을 근거로 대안 검토 |
| Documentation          | Validation             | 코드와 문서의 일치 여부 확인      |

- 각 유형의 공통 요구사항은 중복하지 않고 필요한 세부 조건만 보강한다.
- 작업 도중 다른 유형의 활동이 필요해져도 기존 목적과 제약을 유지한다.
- 추가 작업이 별도 기능이나 큰 구조 변경에 해당하면 분리하여 보고한다.
- 작업 유형의 추가가 수정 권한의 자동 확대로 이어지지 않도록 한다.

## 6. Project Context

공통 프롬프트 기준은 유지하면서 세부 요구사항과 검증 수준은 프로젝트별로 조정한다.

필요한 경우 언어·프레임워크·버전, 아키텍처, 실행 환경, 기술 선택 이유, 도메인 정책, 테스트 환경, 학습 단계, 관련 문서를 반영한다.

예를 들어 WebRTC 프로젝트에서는 연결 상태 및 미디어 자원 정리가 중요한 반면, Backend 프로젝트에서는 트랜잭션과 데이터 정합성이 주요 검증 대상일 수 있다. 어느 한 프로젝트의 기준을 모든 프로젝트에 의무화하지 않는다.

프로젝트 문서와 실제 구현이 다른 경우 차이를 확인하고, 추정으로 한쪽을 사실로 확정하지 않도록 요청한다.

## 7. Scope and Change Control

### 7.1. 범위 내 변경

목표 달성에 직접 필요하고 기존 정책과 양립하는 변경은 작업 범위에 포함할 수 있다. 변경 이유와 영향은 필요한 수준으로 기록한다.

### 7.2. 범위 외 변경

관련 없는 기능 추가, 아키텍처 전환, 불필요한 의존성 도입, 미래 단계 선행 구현, 데이터·업무 정책 변경은 임의로 진행하지 않도록 한다.

범위 밖의 문제가 확인되면 원인·영향·대안을 보고하고 별도 작업으로 분리할지 판단한다.

### 7.3. 작업 중 발견한 문제

현재 작업을 막는 직접적인 문제는 범위 내에서 분석·수정할 수 있도록 하되, 중요한 설계 선택이나 추가 권한이 필요한 경우 결정을 요청하도록 한다.

검토·분석만 요청한 경우 승인 없이 구현으로 전환하지 않는다.

### 7.4. 지침 충돌

작업 요청, 프로젝트 지침, 코드와 문서 사이에 충돌이 있다면 근거와 영향 범위를 확인하도록 한다. 임의로 정책을 바꾸지 않으며, AI 도구의 상위 지침이나 안전 제약을 프로젝트 규칙으로 무효화하려 하지 않는다.

## 8. Validation and Reporting

### 8.1. 검증 기준

검증은 작업 범위와 변경 위험에 대응해야 한다. 필요에 따라 타입 검사, 빌드, 단위·통합 테스트, 실제 실행, 오류·경계 조건, 회귀 검증, 자원 정리, 문서 일치 여부를 포함한다.

모든 작업에 모든 검증을 강제하지 않는다.

### 8.2. 검증 결과 분류

| Status    | Description                            |
| --------- | -------------------------------------- |
| `Passed`  | 실제 수행한 검증에서 기대 결과 확인    |
| `Failed`  | 실제 수행했지만 기대 결과 불충족       |
| `Blocked` | 환경 또는 의존성 문제로 검증 진행 불가 |
| `Not Run` | 해당 검증을 실행하지 않음              |

검증 방법과 환경을 필요한 수준으로 기록하고, 결과가 없는 검증을 `Passed`로 보고하지 않도록 한다. 부분적으로만 확인된 경우 확인된 범위와 남은 범위를 함께 기술한다.

### 8.3. 완료 보고

필요에 따라 변경 내용과 파일, 주요 설계 판단, 수행한 검증, 미완료·미검증 사항, 남은 위험 및 후속 작업을 보고하도록 한다.

실제로 실행하거나 확인하지 않은 작업은 완료로 표현하지 않는다. 작업 규모에 맞춰 보고의 길이를 조정한다.

## 9. Examples

예시는 작성 원칙을 보여주기 위한 것이며 고정된 템플릿은 아니다.

### 9.1. 기능 구현

```text
현재 저장소의 프로젝트 지침과 관련 코드·문서를 확인해주세요.

이번 작업은 브라우저에서 카메라·마이크를 획득하고
로컬 영상 미리보기를 제공하는 기능 구현입니다.

사용자 동작으로 권한을 요청하고, 종료하거나 화면이 해제되면
획득한 모든 미디어 트랙을 정리해주세요.

실제 SFU 송신은 이번 범위에 포함하지 않습니다.

반복 시작·종료, 권한 거부, 비동기 요청 중 종료를 검증하고
실행 결과 및 확인하지 못한 항목을 구분해 보고해주세요.
```

### 9.2. 버그 수정

```text
WebSocket 메시지 크기 초과 시 종료 코드가 예상과 다르게
나타나는 원인을 분석해주세요.
```

## 10. Maintenance

- 실제 프로젝트 작업에서 확인한 문제와 개선 필요성을 바탕으로 규칙을 조정한다.
- 새로운 작업 유형은 반복적인 필요성이 확인될 때 추가한다.
- 특정 프로젝트에만 유효한 세부 요구사항은 해당 프로젝트 문서에서 관리한다.
- AI 도구별 지침 파일 작성·관리 규칙은 AI Project Instructions Convention에서 다룬다.
- 중복된 규칙과 예시를 최소화하고 프롬프트 분량을 획일화하지 않는다.
- 기존에 작성한 프롬프트나 Git 이력을 새 규칙에 맞춰 소급 수정할 필요는 없다.
- Convention 상태와 `Last Updated`는 Repository `README.md`의 공통 관리 규칙에 따라 갱신한다.
